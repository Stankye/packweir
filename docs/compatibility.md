# Compatibility and roadmap

All native adapters are experimental. The [container client matrix](containers.md) qualifies selected authenticated install flows with six real clients against local fixtures using filesystem and S3-compatible storage. Full protocol conformance and broader version coverage remain open. The implementation preserves package bytes while rewriting discovery/download locations. It does not claim Nexus or Artifactory feature parity.

| Ecosystem | Implemented routing | Important limitations |
|---|---|---|
| npm | Packuments, tarball links with SHA-512/SHA-1 binding, JSON security-resource forwarding | No publish, vulnerability-audit POST API, namespace reservation, or automatic provenance retrieval/verification. Download URLs outside configured origins are rejected. |
| PyPI | HTML and JSON simple indexes, distribution/hash links, requires-python/yanked metadata | PEP 658 sidecar advertisement is disabled so clients download the gated distribution. JSON hashes use SHA-256 when supplied. Native attestation retrieval/verification is not implemented. Bzip2, XZ, Zstandard, RAR, and 7z archives are rejected until bounded inspection is implemented. |
| Cargo | Sparse index, generated authenticated config, checksum-bound crate download route; `cargo:token` exercised in the client matrix | No Git index, publishing, owner/yank API, or broader credential-provider/version conformance validation. |
| Maven / Gradle | Artifact paths, POMs, snapshots, metadata, checksum/signature sidecars | POMs and artifacts are gated individually; no publishing, native signature verifier, or snapshot-cache freshness policy. Retained artifact paths must be invalidated explicitly when upstream bytes are mutable. |
| NuGet | V3 service/discovery resource rewriting, package downloads, Basic authentication | No publishing/search conformance guarantee, trusted-signer policy integration, or built-in package signature verifier. Upstream signed package bytes remain unchanged. |

Single byte ranges are served only after complete artifact approval. Multiple ranges and conditional requests are not implemented. The gateway fetches complete bounded responses and does not promise streaming large-artifact performance. Client-provided credentials are never forwarded upstream. Configured upstream bearer secrets are origin-scoped; other upstream authentication schemes need adapters/configuration support.

ZIP inspection and OSV database validation require consistent local and central headers, unique central-directory names, and nonoverlapping entries. Ambiguous archives are rejected even when a permissive client could read them. The ZIP parser is locked to 9.1.3, beyond the affected range of [GHSA-m665-v7pm-7grj](https://github.com/zip-rs/zip2/security/advisories/GHSA-m665-v7pm-7grj); strict consistency validation is explicitly enabled rather than relying on default reader behavior. Packweir 0.1.1 changes the engine version included in evidence fingerprints so previous 0.1.0 approvals cannot survive the inspection change. Upgrade gateways and workers together; packages need fresh analysis under the new fingerprint.

Cache hits reuse retained original bytes and reevaluate current policy. They do not currently revalidate upstream mutable artifact URLs. With `retain=false`, approved bytes are deleted after delivery if no retaining repository or active analysis references them. Denied, abandoned, failed-analysis, and superseded blobs require future garbage collection; there is no automatic retention/TTL collector yet. Job fetch/scan deduplication is database-backed for scans and process-local for fetches. Requests can duplicate upstream work across multiple gateway replicas.

Current jobs are retried up to three times per queued run with lease recovery; exhausted expired leases become failed jobs. Evidence-context changes and manual rescans invalidate existing findings, and lease ownership/context checks prevent old workers from committing stale results. Adapters have wall-clock/output limits; full worker resource scheduling and isolation remain external responsibilities.

[Package identities and scoped policies](policies.md) provide registry-path observations, additive repository and npm-namespace/Maven-group/exact-package requirements, independent delivery fingerprints over shared blobs, and CLI/API explanations. These do not establish publisher ownership, source trust, private/public routing precedence, automatic attestation discovery, or exception/promotion workflows.

Sigstore v0.3 blob signatures, selected source-bound SLSA artifact verification, offline OSV mapped-package checks, and Hipcheck source policies are available through built-in drivers. Discovery, automatic identity mapping, additional builder/statement support, and package-manager-native signatures remain separate work. See the [integration catalog](integrations.md) and [native driver limits](native-drivers.md) for configuration and tool-specific status.

## Milestones

1. **Finish the initial evidence proxy:** Windows compilation, PostgreSQL tests, selected native-client flows, and filesystem/S3-compatible container qualification are implemented; broaden client/version and storage-provider coverage; implement additional trusted scanner adapters, native provenance retrieval/verifiers, complete SBOM validation, license evidence and review models, metrics, safe garbage collection, mutable-artifact freshness, and namespace routing controls.
2. **Deep analysis and advanced clients:** add selective Ghidra/deobfuscation, Assemblyline v4 submission/result integration, automatic agent escalation, OpenSSF Package Analysis, audit APIs, license obligation reports, a supported client/version matrix, and external OCI artifact/report storage through ORAS. OpenDAL remains the blob-storage abstraction; OCI artifact exchange is a separate transport capability.
3. **Hosted repositories:** add private publishing, repository groups, namespace ownership, permissions, quarantine, immutable releases, digest-bound promotion, signing workflows, scoped review/exception workflows, and an administrative UI.
4. **OCI distribution:** add hosted/proxied OCI manifests, blobs, tags, referrers, authentication, and ORAS conformance tests.
5. **Specialized sandboxing:** integrate dedicated DRAKVUF-class workers and optional operator-provided THOR. Assemblyline v4 (ASv4) is the external analysis platform in milestone 2; it is distinct from a dedicated VM execution backend. Available analysis depends on the services deployed in the operator's Assemblyline instance.

Provenance claims, SBOM completeness, vulnerability findings, license obligations, source posture, and malicious behavior are separate evidence categories. No overall score should silently substitute for an explicit required policy check. The [product scope](product-scope.md) defines the proposed assurance boundaries and validation gates; these milestones are planned work, not implemented capabilities or compliance claims.
